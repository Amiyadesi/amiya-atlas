# Atlas 钱的维度：成本地图、账本、项目损益与金钱图谱

目标：把 Atlas 从"记住我有什么"升级为"看清我的钱在哪里、流向哪里"，并成为每天都会打开的软件。资源与关系继续由 Atlas 管理，每一笔实际发生的钱进入账本，二者通过引用连接，在关系图上叠加一层"金钱视图"。

沿用 README 的标准：功能是否值得继续，看用户是否愿意每天主动打开。因此每个阶段都有"真实使用"的完成标准，通过后再进入下一阶段。

## 核心原则

- **约定与实际分开。** Atlas 实体描述"约定"（这台服务器月租多少、哪个项目在用、何时到期），可改。账本记录"实际发生"（某天实际扣了多少），只增不改，写错补冲正。
- **两边互相对照。** 由订阅和事件生成"预期扣费"，实际入账后自动匹配，差额一眼可见。
- **模型只理解，程序负责数字。** 模型提议结构化记录并附上原文依据；金额校验、折算、汇总、损益全部由本地代码完成，模型接口没有写库权限，这条原则保持不变。
- **余额与利润都是算出来的，不存储。** 避免同步冲突，也避免出现两个互相矛盾的数字。
- **内部严谨，界面简单。** 内部采用复式记账，界面保留"一句话"或"金额 + 分类"的快速录入，不要求用户理解借贷。
- **账本条目永远不是图谱节点。** 图谱只展示资源、项目、客户等实体，流水留在账本，节点上限 80 的设计不受影响。

## 数据模型

```ts
// 金额：十进制字符串 + 资产代码，禁止浮点
type Money = { amount: string; asset: string };          // "30.00" USD、"0.00061700" BTC
type Asset = { code: string; decimals: number; kind: "FIAT" | "CRYPTO" }; // JPY 0、USD 2、BTC 8

type AccountKind = "ASSET" | "LIABILITY" | "INCOME" | "EXPENSE" | "EQUITY";
interface LedgerAccount {
  id: string; name: string; kind: AccountKind;
  asset?: string;            // 资金账户的币种或代币
  entityRef?: string;        // 关联 Atlas 实体：Payment Card、交易所账号等
  parentId?: string; archived?: boolean;
}

interface Leg {              // 复式记账的一条"腿"：带符号金额
  accountId: string; money: Money;
  projectId?: string;        // 归属项目（Atlas 实体 ID）
  resourceId?: string;       // 消耗的资源（服务器、域名、订阅等）
}

interface Transaction {      // 不可修改
  id: string; occurredAt: string; precision?: "day" | "month";
  kind: "SPEND" | "INCOME" | "TRANSFER" | "TRADE" | "ADJUST" | "OPENING";
  legs: Leg[];               // 同一资产下各腿之和必须为零
  payee?: string; note?: string;
  refs?: { orderId?: string; subscriptionId?: string };
  source: { captureId?: string; import?: string };
  idempotencyKey: string;    // 防重复入账
  reversalOf?: string;       // 冲正指向被冲正的记录
  createdAt: string;
}

interface AllocationRule {   // 共用成本的分摊规则，带生效期，不回溯
  id: string; resourceId: string; effectiveFrom: string; effectiveTo?: string;
  shares: { projectId: string; weight: number }[];  // 权重和 ≤ 1，剩余记为"闲置容量"
}
```

补充约定：
- 新增 Atlas 值类型 `money`，订阅、服务器、域名、AI 账号的费用字段统一用 Money，取代 `2026-10-15-cost-map.md` 中的 number 方案。账本需要精确计算，两处必须一致。
- 新增实体模板：**Client（客户）**、**Order（接单）**。Order 记录客户、报价、状态、交付日期、所属项目，是"约定"；收款是账本里的流水，二者用 `refs.orderId` 连接。应收 = 报价 − 已收，由程序计算。
- 新增关联类型：`INVOICED_TO`、`ALLOCATED_TO`（分摊规则的展示用边，由规则生成）。
- 预期扣费不新建记录：由实体的费用字段、周期与 RENEWAL / PAYMENT_DUE 事件在运行时推算。
- 持仓与成本批次（Lot）由 TRADE 流水推算，不单独存储；默认先进先出，方法可选，不预设任何税务规则。

## 捕获与提案

沿用 Capture → Proposal → 用户确认 → 加密事务 → 可撤销的整条管线，新增动作类型：`ledger.add`、`ledger.reverse`、`account.add`、`order.add / update`。

- 一句话入账："今天续费 SuperGrok 30 美元，信用卡付的，算 GeoScore 的成本"。提案预览显示账户、金额与币种（加粗）、项目、原文依据。
- **数字守卫**：提案里的金额必须能在原文中找到（统一阿拉伯数字、中文数字、"八块""1.2k"等写法后比对）。对不上则转为 uncertainty 并阻止确认，直到用户亲自修改。语音与剪贴板入口强制二次核对数字。
- 写错了不改，说"撤销刚才那笔"或点"冲正"，生成一条反向记录；最近一次确认仍可使用原有的整体撤销。
- 查询："这个月 GeoScore 赚了多少"由模型解析为结构化条件（时间范围、账户、分类、项目、分组方式、指标），本地执行并显示数字。沿用地区搜索"模型产生条件，本地数据执行"的做法。
- 表单快速录入不经过模型：金额 + 分类 + 账户，默认沿用上次选择，适合高频小额。

## 每天使用的体验

- 首页：快速输入框置顶，下方是本月支出与收入、本月固定成本、即将扣费（来自事件）、本月闲置容量、待确认数量。
- 导航增加"账本"：按日分组的流水、月份切换、搜索、账户余额条、对账入口。
- **对账**：输入账户实际余额，与账本推算值比较，差额一键生成 ADJUST 调整记录并留下原因。这是让账本持续可信的关键习惯。
- 周回顾与月回顾：由本地数字自动汇总（收支、项目损益、异常扣费、续费日历）；模型最多润色文字，不生成任何数字。
- 回溯记账提示：记入已对账的月份时先警告，仍允许，但标记为回溯。
- 已有快捷键、全局快速输入和本地语音继续作为主入口；Android 提供快速录入入口。

## 项目损益与分摊

- 项目损益 = 收入 − 直接成本 − 分摊成本，并显示"闲置容量"单独一项，不硬分给任何项目。
- 直接成本：流水里 `projectId` 指向该项目的支出。
- 共用成本：通过 AllocationRule 按权重分摊，规则带生效期，修改规则只影响之后的月份；报表显示所用规则版本，保证前后可比。
- 判断"关掉某项目能省多少"时使用**可避免成本**视图：只统计关掉后真的会消失的费用，与分摊视图并列显示，二者不混用。
- 平台抽成作为收入流水的手续费腿；可设置"税金预留比例"，收入入账时自动划一部分到预留账户。比例由用户设定，程序不内置任何地区的税率。

## 金钱图谱

在 Explore 增加"关系 / 金钱"切换：
- 节点大小 = 本月成本，颜色深浅 = 成本占比；边标注月度金额。
- 服务器节点旁显示灰色虚线的"闲置容量"。
- 项目节点显示本月收入、成本、利润；点击后侧栏列出最近流水（来自账本，不是节点）。
- 后续加入收入 → 项目 → 成本类别的钱流图（桑基图）。
- 80 个可见节点的上限、一跳展开与现有筛选保持不变。

## 投资与交易计划（BTC）

- TRADE 流水：买入、卖出、手续费、交易所，使用清算账户使每种资产的腿相加为零。
- 已实现与未实现盈亏、持仓成本由本地计算；未实现盈亏使用用户手动输入的价格，首版不接行情。
- **交易计划卡**：入场价、目标价、止损价、盈亏比（程序计算）、冷静期、复盘备注。止损触发后自动生成冷静期提醒与复盘待办。
- 首版不接交易所 API、不保存交易所密钥、不自动下单。Atlas 记录与提醒，不替用户交易。
- 多币种：不跨币种相加；净资产按币种分别显示。可选的汇率表由用户手动录入，带日期，报表注明"汇率截至某日"。

## 同步、备份与兼容

- 账户、流水、分摊规则、客户、订单作为新增加密记录类型，纳入现有 WebDAV 与自建服务器同步。流水不可变，合并时按 ID 取并集，按幂等键去重；冲突只会出现在账户改名、规则修改等可变记录上，沿用逐条确认。
- 旧客户端遇到未知记录类型必须原样保留，不得丢弃，否则同步会吞掉新数据。上线前在同步测试里覆盖这一点。
- 升级前提示导出加密备份；沿用"保存新记录后不要用旧版二进制打开新库"的约定。
- 脱敏导出默认不含金额与备注，只含结构。明文 CSV 导出（给会计或报税）需用户主动发起并二次确认，并提示风险。
- 流水按 `privacy` 分级，SECRET 级别不参与模型匹配，规则与现有一致。

## 验证

- 不变量测试：每笔交易同一资产下各腿之和为零；冲正后净额为零；余额仅由流水推算且重算结果一致。
- Decimal 运算测试：JPY 0 位、USD 2 位、BTC 8 位的加减与舍入；不跨币种相加。
- 分摊测试：权重和不超过 1、剩余计入闲置、规则生效期切换不回溯。
- 持仓测试：先进先出批次、部分卖出、手续费并入成本。
- 本地模型评测：在 `scripts/evaluate-local.mjs` 扩充 30 条以上合成金额输入，覆盖中文数字、多币种、冲正、否定、模糊金额（应进入 uncertainty）、同句多笔；任一数字守卫断言失败返回非零。
- 同步测试：旧客户端保留未知记录；两端各自追加流水后合并为并集；幂等键去重。
- 迁移测试：用临时脱敏库验证旧库升级、旧 `cost` 保留、升级前备份可恢复。
- 性能目标：5 万笔流水下月度汇总与项目损益 < 300 ms（桌面），流水列表虚拟滚动。
- 浏览器测试：录入 → 预览 → 确认 → 冲正 → 撤销；对账差额生成调整。
- 测试与评测只用合成数据，不把真实金额、账号写进仓库。

## 风险与取舍

- **小模型的数字准确率**是最大风险。对策：数字守卫、金额高亮预览、表单录入不经模型、查询由本地计算。
- **复式记账的理解成本**：内部使用，界面隐藏；设置里提供"查看分录"以便学习与排错。
- **范围很大**：靠阶段完成标准约束，任何阶段没有被真实使用就不进入下一阶段。
- **税务与合规**：不内置任何地区的税率与规则，只提供用户设定的预留比例和可导出的明细。
